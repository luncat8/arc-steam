# Ball perspective

## Previous-task review

The rock layer already had a vertical perspective (`rockDrawnY`, `rockScale`,
`rockWorldY`) and the ball was already warped with it, but the ball kept a
constant *width*: `main_draw.js` passed `config.radius` as the horizontal radius
and only multiplied the vertical one. A ball deep in the layer was therefore
drawn as a tall ellipse — it followed the height, not the depth — and no setting
could turn the effect off or show the strike footprint the picture was hiding.

## Implementation

- `index.html`: `PERSPECTIVE` select in the system bar's first row
  (`ball-perspective`: `on` = `Depth scale`, the default; `flat` =
  `Constant size`), plus its `?` mark.
- `js/help.js`: new `perspective` topic (what scales, what never scales, and the
  `F4` overlay), and `F4` added to the `keys` topic.
- `js/main.js`: `ball-perspective` added to the element id list.
- `js/main_draw.js`: `ballPerspective` and `showDamageRadius` view state,
  `ballDrawnScale(y)` (the rock's own `rockScale` law inside the layer, 1×
  outside it and when the setting is off), one scale multiply in the ball pass,
  and `drawDamageRadius` — a dashed ring at `damageRadiusNow(owner) * cell`,
  foreshortened by the same local scale.
- `js/main_input.js`: select binding (marks the scene, never the world) and the
  `F4` toggle, added to `isGameKey`.
- `README.md`: controls row for the selector and `F4`, the perspective
  paragraph, and the test summary.

## Decisions

- **Same law, not a copy.** The ball asks `SteamCeiling.state.rockScale`; there
  is no second curve to keep in sync with the rock.
- **A view rule, not world state.** It lives beside the rock view mode in
  `main_draw.js`, survives New game like the rock shape and ball arrangement,
  and is never read by `physics.js`, `prediction.js` or the ledger.
- **The damage radius gets its own overlay.** Shrinking the ball would
  understate what a strike really spends, so the footprint is drawn separately
  (`F4`, default off) at the owner's real radius in metres. The plan's
  "damage-radius indication stays correct" is met by showing the true radius
  rather than by scaling the ball by it.

## Validation

- `node --test experiments/*.test.js`: 286 / 286 pass, including the new
  interface case: the drawn radius follows `rockScale` at two heights,
  `Constant size` restores a flat radius, the paused chamber keeps `world.time`
  fixed while the picture changes, `F4` adds exactly one ring per ball at
  `damageRadiusNow('rig') * cell` (`0.18 m` drawn body against a `1.097 m` ring),
  hides it again, and New game keeps the setting without touching the purse.
- `node --check` on every changed script; `git diff --check` clean.
- Real Chromium (externally installed Playwright + serverless Chromium, nothing
  added to the repository): the page boots with no console errors, the ball's
  drawn radii follow the layer (a 0.18 m body at 0.08 m at the roof against
  0.4462 = its `rockScale`), `Constant size` and `F4` drive the same state the
  Node test asserts, the new help mark opens its topic, and the extra control
  keeps the system bar inside the viewport from 390 px to 2560 px with no
  horizontal overflow.

## Pitfalls found

- The page keeps `world` inside `main.js`'s scope, so an interface test that
  saved one from `physics.step` before pressing New game is holding the *old*
  world. Read balls through the captured world only after the run that owns
  them has stepped.
- `togglePause` names the *next* action, so a test that toggles blindly depends
  on the pause state the previous test left. Drive it from `#pause` text
  (`setPaused`).
- A paused page still steps a *flying* ball (the pause skips the frame
  accumulator, not a ball already in motion from an earlier edit), so a height
  sample must either be a held ball, or the rock above it cleared so the step
  cannot resolve a contact.
